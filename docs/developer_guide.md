## 1. Setup

### 1.1 Clone and pick a branch

```bash
git clone https://github.com/Rayner3103/CS464.git && cd CS464
git switch learned-selectors
```

| Branch | Holds |
|---|---|
| `learned-selectors` | The newest code: the research harness, the shipped selector and lscli. Work from here |
| `master` | The default branch, and the ref the installer clones. It is behind `learned-selectors` until the two are merged; until then the one-line install fails |
| `learned-selector-cli` | lscli's integration branch (PRs #2-#23), merged into `learned-selectors` by #24 |
| `baseline` | The baseline phase as it stood on 2026-10-19 (before the learned selectors) |

Nothing is committed directly to `learned-selectors` or `learned-selector-cli`. Every change is a branch and a pull
request, reviewed first.

### 1.2 Python environment

Python 3.12 is the tested version. lscli's daemon needs ≥ 3.11 (`tomllib`), and the harness alone runs on 3.10.
Versions are pinned in [`requirements.txt`](../requirements.txt): torch 2.13.0 (+cu130), triton 3.7.1, lightgbm 4.7.0,
scikit-learn, pandas, numpy, matplotlib, nvidia-ml-py, pytest.

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt --extra-index-url https://download.pytorch.org/whl/cu130
python -c "import torch, triton, lightgbm; print(torch.__version__, triton.__version__, torch.cuda.get_device_name(0))"
```

You also need an NVIDIA driver ≥ 580 (the study used 595.99.02), `gcc` and the Python headers (Triton builds its
launcher with them), and `git`. `pipeline/run.sh --check-only` checks all of this. `pipeline/run.sh --only install`
builds the same environment in `pipeline/.venv`, and the pipeline scripts use that one by default.

Run everything from the repo root as `python -m ...`.

### 1.3 First commands

```bash
nvidia-smi --query-compute-apps=pid,used_memory --format=csv   # must list no process before any GPU job
python -m tune env                     # fingerprint -> data/<hw_id>/env.json
python -m pytest -q                    # ~380 tests; most need the GPU, and the GPU must be idle
python -m tune bundle unpack           # optional: the prebuilt kernels (Triton 3.7.1, sm_86 only; 1.5 GiB)
```

### 1.4 Data and models

`data/<hw_id>/` holds every raw result, screen, model and log. It is **gitignored and machine-specific**, so a fresh
clone has none of the 3080's data. What is committed:

* `install/zero_shot.tar.xz`: the RTX 3080's rank v2 Triton ranker, cuBLASLt ranker and router (the set lscli
  starts from). Unpack it with `tar -xJf install/zero_shot.tar.xz -C <dir>`.
* `reports/snapshot/lock1755/`: small copies of 3080 results (benchmark summaries, subsets, picks) plus the cuBLASLt
  ranker (`lt_rank.*`), the router (`router.*`) and the cuBLASLt k-NN table. The code falls back to these when
  `data/<hw>/` has none, but only on the GPU they were built for.
* `kernels/bundle.tar.xz`: the prebuilt Triton kernels.

Rank v1's booster (`lgbm_rank.txt`, ~35 MB) is not committed. Retrain it (`python -m tune topk`, which needs a tune
screen) or copy it from the machine that trained it.

### 1.5 Standard conditions and GPU hygiene

Every number in the reports assumes the SM clock locked at 1755 MHz (`sudo nvidia-smi -lgc 1755,1755`, undo with
`sudo nvidia-smi -rgc`), declared with `python -m tune --clock-lock 1755 <cmd>`, plus the driver the noise study
used. Only compare sessions with the same lock and driver. The rules that have cost data before
([`AGENTS.md` section 7](../AGENTS.md#7-rules-for-agents)):

* Never run two GPU jobs at once, and that includes `pytest` next to a sweep. Check `nvidia-smi` first.
* Long runs go in the background with a log in `data/<hw>/logs/`. Track the real python PID, and kill orphaned sweep
  compile workers by PID.
* If lscli is installed on the machine: `lscli pause` before measuring, and `lscli clock hold` before locking the
  clock yourself. Do **not** `lscli enable-env` the interpreter you develop CS464 with: lscli's own copy of `tune` /
  `kernels` / ... would clash with your checkout (it refuses, but use a separate env).
* Keep held-out shapes out of every fitting step.

## 3. How the selector works

The problem: for one GEMM shape (M, N, K) in fp16, pick the fastest kernel from {a parameterized Triton family of
10,840 valid configs, cuBLASLt's configurations}. The shipped answer is a **ranked short-list plus a short online
timing**, in `tune.online.select_kernel`:

```
shape (M, N, K)
  ├─ Triton half: rank v2 (LightGBM) scores the ~1,200 configs of its pool; the diversified top 3
  │               (top 5 for shapes called ≥ 1M times) are proposed
  ├─ cuBLASLt half: the library's heuristic top 16, plus the 5 configs the learned cuBLASLt ranker predicts fastest
  │                 among every valid config (k-NN proposals from the nearest tune shapes when no ranker exists for this GPU)
  ├─ router (only when the Triton kernels must really compile): time cuBLASLt first, skip the Triton half
  │         when P(Triton wins) < 0.02; re-time the top 3 in reverse order to cancel the timing-order bias
  ├─ each candidate: load from the kernel bundle or compile → correctness gate → 10 cold samples
  └─ the fastest wins and goes into the winner cache (per GPU and software environment)
```

Measured first-use cost per shape: ~0.8 s with compiling, ~0.17 s with the bundle. A cache hit costs ~0.1 ms.

How the pieces were chosen, in the order the study built them (each is a dated update in `reports/week1.md`):

1. **Baselines and gates** (phase 1): the harness, noise floor, B0-B6. Result: the Triton family matches B3+ (G2), and
   per-shape selection matters (G3), but no static portfolio generalizes (G5 fails on held-out shapes).
2. **Selectors**: trivial (B6, k-NN, rules) → learned (10 model families; LightGBM rank form wins) → top-k + short
   online timing → diversified top-k.
3. **Rank v2**: analytic roofline features, near-top row weights, a tail suite as extra tune data.
4. **Joint selection** with cuBLASLt, then k-NN and learned cuBLASLt proposals, then the family router.
5. **Shipping**: kernel bundle, winner cache, lscli.
6. **Transfer**: an RTX 2060 (sm_75, no tensor-core path in Triton) and an RTX 3090 (sm_86), zero-shot and retrained.

## 5. Results

RTX 3080, standard conditions. Details and caveats: [`AGENTS.md` section 6](../AGENTS.md#6-key-results-so-far-rtx-3080-standard-conditions)
and the dated updates in [`reports/week1.md`](../reports/week1.md).

| Gate (plan 8.2) | Status |
|---|---|
| G1 measurement validity | **Pass** for kernels ≥ 50 µs: tie margin ε = 2 % (5 % below 50 µs). Unlocked clock: same ε across sessions, but one short online timing needs ~4 % |
| G2 Triton family ≥ 90 % of B3+ | **Pass**: median 98.8 % over 160 shapes |
| G3 selection has value | **Pass**: the best single config is a median 68-74 % off the per-shape best |
| G4 beats B3+ (searched cuBLASLt) | **Fails** at ≥ 50 µs (0 of 86 held-out shapes > 5 % faster); narrow pass for tiny GEMMs |
| G5 a small static portfolio suffices | In-sample pass; **fails held-out** (p95 plateaus at ~8-9 %) |

Conclusion: not viable as a cuBLAS competitor on this GPU, viable as a **selection** project, so the target became
selecting across {Triton ∪ cuBLASLt}.

The shipped selector (rank v2 top-3 + cuBLASLt top-16 + learned cuBLASLt ranker top-5), regret against the best
candidate in its pool:

| Shapes | median | p95 | p99 | mean | vs B2 (cuBLASLt default) | vs B3+ |
|---|---|---|---|---|---|---|
| 86 held-out | 0.5 % | 5.5 % | 8.4 % | 1.4 % | median 0.91 (heuristic-only pool, 2026-11-01) | geomean 1.001 at ≥ 50 µs (a tie); 0.951 below |
| 60 fresh shapes (in no suite) | 0.6 % | 5.6 % | 12.8 % | 1.6 % | median 0.924 (42 faster / 1 slower) | 1.000 |

Other GPUs: on the RTX 3090 (sm_86) rank v2 used zero-shot is within noise of the 3090's own retrained model, and the
joint search lands at 0.99-1.00 of B3+. On the RTX 2060 (sm_75), Triton has no tensor-core path, so the Triton
rankers do not transfer and cuBLASLt carries the search. See [`reports/cross_gpu.md`](../reports/cross_gpu.md) and the
2026-11-02 to 2026-11-10 updates.

## 6. Common tasks

### 6.1 Run the tests

`python -m pytest -q` on an idle GPU. CPU-only subsets exist for analysis code (e.g.
`python -m pytest -q tests/test_zero_shot.py tests/test_cross_gpu.py`).

### 6.2 Reproduce the study

`pipeline/run.sh --quick` (about 4-5 h) or `--full` (a day or more) builds a venv, measures, sweeps, trains and validates
into `pipeline/runs/<mode>-<ts>/`, never into `data/`. Lock the clock first. See [`pipeline/README.md`](../pipeline/README.md).
The individual commands of the original runs are in [`AGENTS.md` section 8](../AGENTS.md#8-reproduce-the-main-pipeline).

### 6.3 Train the shipped selector on a new GPU

```bash
sudo nvidia-smi -lgc <MHZ>,<MHZ>       # ~80-85 % of the card's max SM clock; or --clock-lock none --allow-unlocked
pipeline/train_best.sh --full --clock-lock <MHZ> [--with-bundle] [--skip-validation]
```

It runs rank v1 + v2, the cuBLASLt screen and ranker, the stage 2 and router, an optional bundle, and held-out
validation (`--list-stages`; resumable with `--resume <run dir>`). That is about 35 h on a 3080 (extrapolated);
`--quick` is for slow cards. Output: `pipeline/runs/train_best-<mode>-<ts>/`, with `models/INSTALL.md` saying where
each file goes. On a SLURM cluster: `sbatch remoteGPU/train_best.sh`. lscli runs the same script stage by stage in
idle time.

### 6.4 Zero-shot transfer to another GPU

`pipeline/zero_shot.sh --quick --clock-lock <MHZ>` runs the 3080's rankers on this GPU with no refit and scores them
against this GPU's own held-out screen. The manual version, with how to read the report, is
[`docs/zero_shot_runbook.md`](zero_shot_runbook.md). Compare runs on different GPUs with `python -m analysis.cross_gpu`.

### 6.5 Other tasks

| Task | How |
|---|---|
| Redraw the overview figures and `reports/results_overview.md` | `python -m analysis.plots` (CPU only, safe next to a GPU job) |
| Add a backend | Expose `make_runner(a, b, out=None)` and register a spec in `tune.runner.candidates_for`, so it is validated and timed like the rest ([`AGENTS.md` section 4](../AGENTS.md#backend-spec-strings---backends-comma-separated-runnercandidates_for)) |
| Rebuild the kernel bundle (after a Triton upgrade, a kernel edit or a retrained ranker) | `python -m tune bundle build && python -m tune bundle verify --per-shape 0 && python -m tune bundle pack` ([`docs/kernel_bundle.md`](kernel_bundle.md)); each committed archive adds ~25 MiB to git history |
| Repack lscli's starter models | `python install/pack_zero_shot.py --triton ... --lt-rank ... --router ... --hw-id ... --out install/zero_shot.tar.xz` (reproducible; docstring has the command) |
| Measure the noise floor | `python -m tune --clock-lock 1755 noise --rounds 3 --repeats 50 --n-allocs 3`; compare sessions with `python -m analysis.noise_compare` |
| Write up a finding | A dated `## Update YYYY-MM-DD: ...` at the top of `reports/week1.md` with what ran (session ids, row counts, invalid rows), the tables, gate changes and reproduce commands; small artifacts to `reports/snapshot/` |

## 7. Working on lscli

The contract is [`docs/lscli/spec.md`](lscli/spec.md): file formats (section 3), daemon (4), client (5), CLI (6),
worker protocol (7), installer (8), limitations (9). Change the spec together with the code.

| Component | Runs in | Code |
|---|---|---|
| client (torch patch) | the user's own env, via `lscli.pth` | `lscli/client.py`, `lscli/boot.py`, `lscli/guard.py` |
| worker (compile, validate, time one pool) | the user's interpreter, started by the daemon | `lscli/worker.py` |
| daemon (idle gate, scheduler, jobs, training, models) | lscli's own venv (`lscli.service`) | `lscli/daemon.py`, `gate.py`, `scheduler.py`, `jobs.py`, `training.py`, `models.py` |
| proposer (cuBLASLt ranker picks; needs the GPU) | lscli's venv, per search job | `lscli/propose.py` |
| CLI | lscli's venv | `lscli/cli.py`, `doctor.py`, `config.py` |
| installer, unit, clock helper | — | `install/` |

Rules that must hold ([`AGENTS.md` section 6b](../AGENTS.md#6b-lscli-the-selector-as-a-service)):

* **The daemon process never creates a CUDA context.** Everything that touches the GPU runs in a job. Otherwise NVML
  lists the daemon as a compute process and its own idle gate never opens.
* Winners are timed in the user's interpreter and written only after a final gate check.
* `select_kernel(tune.online.LT_ONLY, ...)` means "no ranker yet". `None` is the tests' placeholder for a faked
  search.
* Daemon measurements are not study data. Never write them into `data/<hw>/` or reports.

Tests: `tests/test_lscli_*.py` (client overhead budget, daemon end to end, install, gate, training orchestration).
To try a change for real, commit it and install your branch from the checkout (user guide
[1.3](user_guide.md#13-a-pinned-ref-or-from-a-clone)):
`bash install/install.sh --repo "$PWD" --ref <your branch> --reuse-site "$(command -v python)"`. `--reuse-site` borrows
your environment's packages instead of downloading 3 GB. The install replaces any other lscli install of your user. Then run `examples/lscli_demo.py` as in the user guide's "Try it out" from outside the
checkout.

## 8. Open items

Collected from [`AGENTS.md` section 9](../AGENTS.md#9-open-next-steps), [`docs/lscli/plan.md` section 4](lscli/plan.md#4-open-after-v1)
and [spec section 9](lscli/spec.md#9-known-limitations-v1) (2026-11-18).

**Release**

* Merge `learned-selectors` into `master`. The installer and the user guide install from `master`, which has no
  `install/` or `lscli/` yet.

**Selector**

* Ranking: lambdarank / regression blends, a larger candidate pool, better ranking for N = 1 and tiny-K shapes,
  near-optimal tiles ranked low.
* Joint search: a wider fix of the timing-order bias (interleaved timing), the joint selector in the zero-shot
  runbook, faster rank v2 ranking (+40 ms).
* Kernel-level gaps that selection cannot fix: an aligned-copy or padded path for unaligned strides, and a fused or
  atomic split-K reduction.
* Not built: B4 (CUTLASS), per-candidate subprocess isolation with hang timeouts, adaptive sampling.

**Measurement**

* A noise study for graph-amortized timing (a second session plus a reboot) before relying on tiny-GEMM wins.
* RTX 3090: a second noise session or a locked-clock run (its cross-session floor is unknown).
* Daemon conditions: noise on other GPUs, with the desktop in use, and graph timing under 50 µs.

**Other GPUs**

* RTX 3090: a fresh-shape check, the 3080's cuBLASLt ranker and router zero-shot on it, `bundle verify` with both
  pools run on the 3090 itself, and retraining its rank v2 with the current `v2_hp` rule (#13).
* Another tensor-core generation (Ada, Hopper) is untested.

**lscli**

* NT / TN layouts (`nn.Linear`): the cuBLASLt transpose flag, an NT axis in the training suites, layout as a ranker
  feature.
* Multi-GPU and a shared multi-user service.
* Move the vendored packages under an `lscli._vendor` namespace, which removes the package-name clash.
* Pruning the usage profile, which never drops a shape.
